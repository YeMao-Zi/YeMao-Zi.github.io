# 一 需求概述

## (一) 需求背景

### 1 业务背景

店铺在运营过程中，商家可能需要修改两类强管控信息：

- **企业认证信息**：法人姓名、证件类型 / 证件号、证件照片、企业资质（经营注册号 / TIN / VAT）、资质文件、董事身份证件、完税证明、特许经营协议等；
- **收款信息**：银行账户（银行账户名、银行名称、银行账号、银行品牌、持卡人姓名）与 EcoCash（账号名、账号）。

这两类信息直接关系到店铺的主体资格与结算资金去向，属于平台必须核验的关键资料。

目前商户端「店铺设置」中，企业认证信息与收款信息点「编辑 → 保存」后**立即生效**，平台没有审核环节：若商家填写的资质不实、或收款账号被篡改，平台无法在生效前发现并拦截，存在主体资质不实、结算资金被恶意变更的风险。

因此，需要对企业认证信息与收款信息的修改增加平台审核：**审核期间店铺设置仍展示原信息，审核通过后新信息才生效**；平台管理端通过店铺列表的「信息变更」入口查看原值与新值完成审核。

### 2 用户现状与痛点

- **平台侧无审核环节**：商家修改主体资料或收款账户后直接生效，平台无法在生效前核验，存在合规与资金风险。
- **商家侧反馈缺失**：修改后立即生效，商家无法确认平台是否认可本次变更；若填写有误也缺少二次确认。
- **运营侧缺少统一入口**：平台缺少「信息变更」待办视图，无法按「有待变更」快速筛选并集中处理。

## (二) 需求范围

基于以上需求背景，本次需要实现的需求有：

- 需求一：商户端「企业认证信息」修改提交后进入「审核中」，**审核期间店铺设置显示原信息**。
- 需求二：商户端「收款信息」修改提交后进入「审核中」，审核期间显示原信息。
- 需求三：平台审核通过后新信息生效；驳回后保留原信息，商户端展示拒绝原因，商家可修改后重新提交。
- 需求四：平台管理端店铺列表增加「信息变更」筛选与「待变更」标识，通过「信息变更」入口查看原值 / 新值并审核（通过 / 拒绝）。
- 需求五：一次提交可包含多个模块（如企业认证信息 + 收款信息），合并为一个申请整体审核。

## (三) 核心指标

- 核心指标一：企业认证信息、收款信息的修改全部经平台审核后生效，覆盖率 100%。
- 核心指标二：审核期间对外始终使用原信息，因未审核变更导致的资质 / 资金风险事件为 0 起。
- 核心指标三：信息变更申请的平台平均审核时长（提交 → 处理完成）不超过 1 个工作日。

## (四) 主要风险

- **资金安全**：收款账户变更直接影响结算资金去向，属高风险操作，需严格核验并全程留痕（提交人、提交时间、审核人、审核时间、拒绝原因）。
- **体验风险**：审核期间显示原值，商家可能误以为修改未保存成功；需在模块顶部以提示条明确说明「已提交、待审核、当前仍显示原信息」。
- **口径一致性**：审核期间允许继续编辑，若平台审核的是历史提交内容，会出现「审的旧提交、生效的新值」不一致；需统一为 **以最后一次提交为准**，并在审核弹窗展示本次提交时间。
- **驳回体验**：驳回必须给出明确原因，避免商家反复无效提交。

## (一) 流程设计

### 类型 B 流程：店铺信息变更提交与平台审核

```
sequenceDiagram
    participant M as 商户端
    participant S as 系统
    participant P as 平台管理端

    M->>M: 店铺设置 → 企业认证信息 / 收款信息 → 编辑
    M->>S: 保存并提交变更
    S->>S: 记录变更申请（原值快照 + 新值），状态 = 待审核
    S->>M: 模块顶部显示「信息变更审核中」，字段回显原值
    Note over M: 审核期间可再次编辑提交，以最后一次为准
    P->>P: 店铺列表筛选「有待变更」→ 点击「信息变更」
    P->>P: 查看原值 / 新值对照 → 选择审核意见（通过 / 拒绝）
    alt 审核通过
        P->>S: 确认通过
        S->>S: 新值生效，清除待审申请
        S->>M: 提示条消失，展示新信息
    else 审核拒绝
        P->>S: 确认拒绝（选择拒绝原因）
        S->>S: 保留原信息，记录拒绝原因
        S->>M: 提示条变红「变更已驳回 · 原因：{拒绝原因}」，可修改后重新提交
    end
```

流程文字描述：

- 商家在商户端「店铺设置」中编辑企业认证信息或收款信息并保存；系统校验是否存在修改，若存在则记录一条信息变更申请（含各字段原值快照与提交的新值），状态置为「待审核」。
- 提交成功后，商家端该模块字段**回显为原信息**（审核期间始终显示原值），模块顶部出现橙色提示条说明「信息变更审核中」及本次提交时间、变更项数量。
- 审核期间商家可继续编辑并提交，系统以最后一次提交为准，覆盖该申请的待审内容与提交时间。
- 平台运营人员在店铺列表中筛选「信息变更 = 有待变更」，通过操作列的「信息变更」入口打开审核弹窗，查看各变更模块的「字段 / 原值 / 新值」对照。
- 运营人员选择审核意见：选「通过」直接确认；选「拒绝」需选择拒绝原因后再确认。
- 通过后新信息生效、提示条消失；拒绝后店铺保留原信息，商家端展示拒绝原因并允许修改后重新提交。

# 三 商户端功能说明

## (一) 审核态通用规则（企业认证信息 / 收款信息共用）

**1 功能用途**：商家提交变更后，明确告知当前处于审核中或已驳回状态，并说明此时店铺设置仍显示原信息。

**2 功能原型**：

路径：商户端 → 店铺设置 → 企业信息 / 收款信息 → 卡片顶部提示条

[预留位置放原型图]

**3 功能逻辑**

- 提示条位于模块卡片标题下方、字段之上，样式随状态变化：

- **审核中**：橙黄底提示条（底 `#fffbe6`、边框 `#ffe58f`、字 `#ad6800`），文案「**信息变更审核中** · 已于 {提交时间} 提交（{N} 项），平台审核通过后生效，审核期间此处仍显示原信息」。
- **已驳回**：红色提示条（底 `#fff2f0`、边框 `#ffccc7`、字 `#cf1322`），文案「**变更已驳回** · 原因：{拒绝原因}，可修改后重新提交」。

- 提示条左侧图标使用内联线性 SVG（审核中=时钟、已驳回=警告）。
- 审核期间模块仍可编辑：商家再次保存并检测到修改时，更新本次申请（覆盖待审内容与提交时间），**以最后一次提交为准**；未检测到修改时提示「未检测到修改」，不生成新申请。
- 审核通过后提示条消失，模块展示新信息；驳回后模块始终展示原信息，直至重新提交并通过。

**4 数据需求**

**埋点：**

- 变更提交：记录商家提交信息变更的事件，携带店铺编号、变更模块、变更项数量、提交时间。
- 审核态提示条曝光：记录提示条展示的事件，携带店铺编号、状态（审核中 / 已驳回）与变更模块。
- 驳回原因曝光：记录已驳回提示条展示的事件，携带店铺编号与拒绝原因分类。

**5 验收标准**

**功能要求：**

- 保存存在修改的企业认证信息 / 收款信息后，模块字段回显为原信息，并展示「审核中」提示条。
- 审核期间再次修改并保存，待审申请被覆盖，提示条展示最新的提交时间与变更项数量。
- 未做任何修改直接保存时提示「未检测到修改」，不生成申请。
- 审核通过后提示条消失且展示新信息；驳回后始终展示原信息并显示拒绝原因。
- 中英文切换时提示条文案正确同步切换。

## (二) 收款信息变更提交

**1 功能用途**：商家修改银行账户 / EcoCash 收款信息并提交平台审核，防止结算账户被恶意篡改，保障资金安全。

**2 功能原型**：

路径：商户端 → 店铺设置 → 收款信息

[预留位置放原型图]

**3 功能逻辑**

- 商家点击「编辑」进入可编辑态，修改以下字段后点击「保存」，系统提交变更申请：

- 银行账户：银行账户名、银行名称、银行账号、银行品牌、持卡人姓名；
- EcoCash：EcoCash 账号名、EcoCash 账号。

- 提交成功后提示「已提交，等待平台审核」，模块字段回显原信息，展示「审核中」提示条。
- 平台审核通过后，新收款信息生效（后续结算按新账户执行）；审核驳回后保留原账户并展示拒绝原因。
- 收款信息为资金相关高风险信息，平台审核时应重点核验账户名与店铺主体 / 营业执照的一致性。

**4 数据需求**

**埋点：**

- 收款信息变更项：记录本次变更涉及的字段名称与新值，用于平台审核对照展示。
- 收款账户变更提交：记录事件，携带店铺编号、变更字段数量与提交时间。

**5 验收标准**

**功能要求：**

- 修改任一收款字段并保存后，变更申请包含对应字段的原值与新值。
- 审核期间结算仍使用原收款账户，不因待审变更而改变资金流向。
- 审核通过后，结算账户切换为新收款信息。
- 驳回后原收款账户不变并展示拒绝原因，商家可修改后重新提交。

# 四 平台管理端功能说明

## (一) 店铺列表「信息变更」筛选与待变更标识

**1 功能用途**：平台运营人员在店铺列表中快速筛选出存在待审信息变更的店铺，并进入审核。

**2 功能原型**：

路径：平台管理端 → 店铺管理 → 店铺列表 → 筛选栏「信息变更」/ 状态列 / 操作列

[预留位置放原型图]

**3 功能逻辑**

- 筛选栏提供「信息变更」下拉，选项为：全部（默认） / 有待变更 / 无待变更。

- 选择「有待变更」：仅展示存在「待审核」信息变更申请的店铺；
- 选择「无待变更」：仅展示不存在待审申请的店铺。

- 存在待审变更的店铺：

- 状态列在店铺状态标签后追加橙色「待变更」标识；
- 操作列在通用入口后出现橙色「信息变更」入口，点击打开审核弹窗。

- 无待审变更的店铺不展示「信息变更」入口；已驳回的申请（商家未重新提交）不计入「有待变更」。

**4 数据需求**

**埋点：**

- 信息变更筛选：记录筛选操作事件，携带筛选条件（有待变更 / 无待变更）与结果条数。
- 待变更标识曝光：记录列表中「待变更」标识的展示事件，携带店铺编号。

**5 验收标准**

**功能要求：**

- 筛选「有待变更 / 无待变更」结果正确，与店铺实际待审申请一致。
- 待审店铺状态列正确展示「待变更」标识，操作列正确出现「信息变更」入口。
- 无待审申请时不展示「信息变更」入口。
- 中英文切换时筛选项、标识与入口文案正确同步切换。

## (二) 信息变更审核弹窗

**1 功能用途**：平台运营人员查看变更内容（原值 / 新值对照），选择审核意见并完成通过或拒绝。

**2 功能原型**：

路径：平台管理端 → 店铺管理 → 店铺列表 → 操作列「信息变更」→ 审核弹窗

[预留位置放原型图]

**3 功能逻辑**

弹窗自上而下为固定三段结构：

1. **变更内容对照**：展示申请时间与当前状态（待平台审核）；按模块分组（企业认证信息 / 收款信息 / 店铺信息等），每组以表格展示「字段 / 原值 / 新值」三列，仅列出发生变化的字段；原值弱化灰、新值深色加粗并浅蓝底强调；文件类字段以文件名链接展示，可点击查看。
2. **审核意见（常驻）**：「通过 / 拒绝」二选一的分段按钮，默认选中「通过」（蓝底），选择「拒绝」时按钮变红底。

- 选择「拒绝」时，其下展开「拒绝原因（必填）」下拉，选项为：资料不完整 / 信息填写有误 / 证件照片不清晰 / 与营业执照不一致 / 其他；
- 选回「通过」时自动收起并清空拒绝原因。

1. **底部按钮（常驻）**：「取消（次按钮）/ 确认（主按钮）」，按钮固定不随审核意见切换。

点击「确认」的处理口径：

- 审核意见为「通过」：将变更内容写回店铺（详情等展示处立即更新为新值），清除待审申请，提示「已通过「{店铺名称}」的信息变更申请，新信息已生效」。
- 审核意见为「拒绝」：未选择拒绝原因时提示「请选择拒绝原因」且不关闭弹窗；选择原因后置为已驳回并记录拒绝原因，店铺保留原信息，提示「已拒绝「{店铺名称}」的信息变更申请」。
- 取消 / 关闭 / 右上角 × 均关闭弹窗，并将审核意见重置为「通过」、收起拒绝原因。

**4 数据需求**

**埋点：**

- 审核弹窗打开：记录事件，携带店铺编号、申请时间、变更模块与变更项数量。
- 审核结果提交：记录事件，携带店铺编号、审核意见（通过 / 拒绝）、拒绝原因分类（拒绝时）与审核人、审核时间。
- 审核时长：记录从申请提交到审核完成的时间差，用于统计平均审核时长。

**5 验收标准**

**功能要求：**

- 弹窗正确展示各模块的「字段 / 原值 / 新值」对照，仅包含发生变化字段，文件类字段可点击预览。
